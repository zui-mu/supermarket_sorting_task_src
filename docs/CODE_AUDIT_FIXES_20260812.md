## 一、已修复：裁判计分（referee.py）

### F1【致命】已交付/已掉落商品被反复误判为"碰倒"（C2，每流程 -5）
`_toppled_other_object` 只排除了当前夹持目标。第一件商品交付后，它在配送框里的位置
与初始货位相差数米，后续每个流程都会因为 `xy_shift > 0.05m` 被判定 C2 扣 5 分。
**修复**：新增 `retired` 集合（已计分/已掉落目标不再参与 C2），并新增
`toppled_penalized` 集合（同一倒伏物只扣一次 C2）。同时把"当前正被双指夹持"的目标
排除出 C2 判定，避免 S3 绑定目标的同一帧误扣 C2。

### F2【严重】S2 触发后 `touched` 冻结，误触/换目标会让流程永远卡在 S2
原先只在 step==1 记录 touch，S3 只允许绑定 `touched` 里的目标。机器人先碰到 A、
实际夹走 B（或重试后换目标）时，S3 永远不触发，`self.flow` 永久占用，之后整个
比赛无法再开新流程计分。
**修复**：step 1/2 持续累积 touch；S3 优先绑定 touched 目标，但允许绑定任何
"双指夹持 + 撤出货架位移达标"的剩余目标。

### F3【严重】物体落在高台面（货架/桌面）时流程永远卡在 S3
原掉落判定要求 `z < 0.30`（地面）。物体掉在货架层板（z≈0.5~1.2）或桌面上时
不算掉落，流程卡在 S3，同样导致全程无法再计分。
**修复**：step 3 未夹持时，若目标 `z < drop_z` 或"静止且持续未夹持超过
`ungripped_rest_s`（默认 1.2s）"则判掉落；目标已在配送框内静置的直接按 S4+S5
结算，避免把一次成功放置误判成掉落。

### F4【严重】流程无超时作废机制
任何无法推进的流程都会永久占用裁判状态。
**修复**：新增 `flow_timeout_s`（默认 240s）——流程自上次步骤推进起超时即作废
（不计分/不扣分），下次进入取货区自动开新流程。

### 仿真实测结论与遗留项（如实记录，第四轮：激光根因 + 避障闭环）

**最关键发现——激光雷达从未工作过**：官方镜像的 mujoco_lidar 只有 CPU 后端
（taichi 未装），其 `trace_rays` 返回全 ≈0.02m 的垃圾数据；客户端 `valid>0.12`
过滤后所有避障扇区恒为空——这解释了团队历史所有运行中 `[avoidance]` 计数为 0、
所有撞箱 C1。已修复：server 端增加启动自检（一次探测扫描 max<1m 即判定不可用）
并回退到自研 `mj_ray` 扫描器（MuJoCo 内置射线，无新依赖；`bodyexclude` 必须排除
`agv_link` 底盘体——它不含子树，排除根体无效，射线会打在 0.02m 处的自身网格上）。

在此基础上连续修复并实测验证（第 5~28 轮）：
- **恢复返回值语义 bug**：`follow_route` 把 `start_delivery_collision_recovery` 的
  True（恢复已启动）当成 True（路线完成）返回 → 在距配送台 2.5m 处进入 PLACE 并
  在半空开爪（C3 掉落）。已改为返回 False。
- **恢复动作过猛**：装载恢复原地旋转 0.55 rad/s 把夹持物甩出（C3）。已限速到
  商品载重角速度。

## 九、第二十二轮（第 75 轮：server 中途退出根因闭环 + 存活加固）

用户自行排查确认的三个故障链，本轮全部在代码层闭环：

- **根因链**：discoverse 的 `step()` 里物理与渲染同线程 —— 渲染异常/卡顿会
  冻结里程计（客户端表现为"cmd=0.85 但里程计几秒不动"）→ 触发 stuck recovery
  循环 → 消耗整场时间；而 `glfw.window_should_close()` 一旦返回 True 就把
  `running` 置 False。旧 server 主循环 `while rclpy.ok() and exec_node.running`
  随即退出，且 `finally` 落盘裁判结果后容器 Exited(0) —— 与用户观察完全吻合
  （"server 中途退出"、日志停在 "referee results saved"）。验证脚本实际跑在
  `MUJOCO_GL=egl SUPERMARKET_HEADLESS=1`，无窗口，`window_should_close` 根本不
  被轮询，真实退出路径是渲染异常被主循环 `break` 吞掉。

- **修复（supermarket_sorting_server.py + mmk2_ros2.py）**：
  1. 模块级补丁 `glfw.window_should_close = lambda _: False`（mmk2_ros2 导入即

  2. 双主循环改为持久循环 + `running` 复置守卫（`%240` 限频告警）；
  3. **渲染/物理异常不再 break**：`mj_step` 先于 `render` 执行，单步渲染失败时

  detections 输出 world 坐标稳定；搜索模式"扫描货位→识别类别→绑定到 detected product"链路能跑。
- **发现的卡点**：搜索模式几乎每个货位 deploy 后 "vision target timeout during deploy;
  anonymous search candidate was not visually locked"→ 无法抓取。
- 根因1（已修）：SEARCH_DETECT_TIMEOUT 2.5s 太短，6 FPS + YOLO 推理 + 3帧类别共识 +
  N帧位姿稳定在 2.5s 做不完 → 已改 12s。
- **根因2（未修，关键）**：det 中被大量 height_reject(23)/assoc_reject(14) 拒绝，
  检测到的 zhijin 世界 z=0.50，而真实 L2 层 z≈0.895（L3≈1.23）——**YOLO 深度→世界坐标
  有 ~0.4m 高度偏差**，或识别选错货位。GT 模式直接给真值所以从未暴露此问题。
- **根因3（环境）**：runtime_layout.json 的 aruco_id/shelf/level 关联乱（slot_B_L2_C1 标 A L2 C1、
  aruco 3；多个 zhijin 混在 A 架 L2/L3），随机化布局时关联错乱，搜索任务与真实货位对不上。
- 待排查：感知节点 pixel_to_cam + T_cam_world 的深度标定（z 偏差来源）；
  以及随机化时 aruco 关联是否可靠。这影响正式匿名任务能否正确锁定目标。
- 已提交：SEARCH_DETECT_TIMEOUT 修复（Round 61e）。
