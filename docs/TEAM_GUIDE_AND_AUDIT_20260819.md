## 一、整个程序是怎么运行的（七层讲解）

用打游戏来类比：**仿真 = 官方给的"游戏机"（Docker 容器）+ 你的代码（机器人"大脑"）+ 虚拟世界画面（窗口）**。

### 第 1 层：服务器创建比赛场景

文件：[supermarket_sorting_server.py](https://github.com/zui-mu/supermarket_sorting_task_src/blob/main/examples/supermarket_sorting/supermarket_sorting_server.py)

服务器启动时做的事：
1. 读取货架、商品、障碍物配置文件；
2. 按**随机种子**打乱商品在货架上的位置（同一 seed 结果相同，不同 seed 不同）；
3. 随机生成箱子障碍位置（可开关）；
4. 把场景写成 MuJoCo 能读的 XML；
5. 发布机器人传感器数据（关节、相机、雷达、里程计）；
6. 发布本局任务清单（要拿哪几个商品）。

**关键点**：同一场仿真中，障碍物初始位置**不会自动变化**（除非被机器人撞动）。重启服务器或换 seed 才会重新随机。

### 第 2 层：服务器决定"要拿什么"

- `SUPERMARKET_TASK_COUNT=5`：本局 5 个任务；
- `SUPERMARKET_TARGETS=kele`：全部是可乐；
- 决策器（`decision/order_scheduler.py`）按固定顺序排任务：先按货架 X 坐标从左到右，同一列先中层 L2 → 上层 L3 → 下层 L1。

**所以"为什么要拿这个"不是机器人临时看见哪个就拿哪个**，而是：
> 服务器先发布 5 个可乐任务 → 决策器按货架位置选下一个 → 机器人前往对应货架格。

### 第 3 层：两种模式的区别（非常重要）

**你看到可视化时跑的是"开发测试模式"**，脚本 `run_visual_unlimited.sh` 里写着：

```
SUPERMARKET_SEED=11
SUPERMARKET_TASK_COUNT=5
SUPERMARKET_TASK_ANONYMOUS=0      # 任务不匿名（直接告诉是哪个商品）
SUPERMARKET_TARGETS=kele           # 全部可乐
SUPERMARKET_DETECT_BACKEND=gt      # 感知用"真值"（仿真直接告诉物体位置！）
SUPERMARKET_ALLOW_RUNTIME_LAYOUT=1 # 允许读取运行时货架布局（直接知道每个商品在哪格）
SUPERMARKET_TEST_ORACLE=1          # 本地裁判 oracle（把裁判信息开放给客户端）
```

**这意味着**：可视化模式下，机器人**不是靠相机识别**找到商品的——是仿真程序直接告诉它"商品 A 在第 B 货架第 C 格"。这适合调机械动作（抓、放、走），**不代表正式比赛的识别能力**。

**正式比赛模式**（`SUPERMARKET_TASK_ANONYMOUS=1` + YOLO 感知）：
- 任务只给"商品种类"（如可乐），不告诉在哪个格；
- 机器人要自己**看**：头部相机 → YOLO 识别出可乐 → 深度 → 世界坐标 → 结合货架 ArUco 标记 → 判断"这个格里的可乐是不是我要的" → 绑定任务。

### 第 4 层：正式模式怎么靠相机找商品

感知节点 `perception/kele_detect.py` 订阅：头部彩色图 + 深度图 + 相机内参 + 关节角 + 里程计。

流程：
1. YOLO 在彩色图里框出商品；
2. 取框中心附近的深度中值（物体离相机多远）；
3. 用相机内参把"像素 + 深度"变成"相机坐标下的三维点"；
4. 用关节角做正运动学，算出头部相机在世界中的位置；
5. 把目标从相机坐标变换到世界坐标；
6. 多帧观察，做中值滤波（去掉抖动）；
7. 结合货架 ArUco 标记，把商品类别和货架格绑定；
8. 判断是否属于当前订单。

**而 `gt` 后端跳过了 1-6 的"真识别"，直接读仿真真值**。所以要把"动作控制测试"和"正式感知测试"分开看。

### 第 5 层：抓取状态机（机器人的"动作剧本"）

主程序 `supermarket_sorting_client.py`（6300+ 行）的阶段：

```
NAV_SHELF  导航到货架前
→ DEPLOY   伸出机械臂到预抓取点
→ CREEP    底盘缓慢向前蠕动（手臂基本冻结）
→ CLOSE    停住，等 0.35 秒，缓慢合爪
→ LIFT     抬升商品
→ VERIFY_GRASP  判断是否真夹住了（夹爪关节位置+力矩+裁判信息）
→ NAV_TABLE 保持搬运姿态，导航到终点桌
→ PLACE    下降、开爪、后退一点
→ DONE     本单完成，选下一单
```

### 第 6 层：它怎么知道爪子在哪

**不是靠摄像头**，而是：
1. 读机械臂关节角；
2. 用运动学模型（FK 正运动学）算出末端位置；
3. 用逆运动学（IK）算"要到达目标位置，各关节该转多少"；
4. 用夹爪开合位置和电机负载判断是否夹到东西。

**关键**："系统认为爪子在哪"和"爪子实际是否精确对中"是两回事。关节角没错，不代表相机标定、模型误差、底盘朝向误差不存在。末端几厘米内没有视觉闭环，就会出现单侧手指先碰瓶。

### 第 7 层：导航方式

项目自写了一个小型八方向网格 A*（`navigation/grid_planner.py`）：
- 墙、货架、桌子 = 静态障碍；
- 雷达点 = 动态障碍；
- 障碍做膨胀（给底盘留安全距离）；
- A* 找路径 → 直线剪枝减少拐点；
- **平时默认走预设走廊**，撞到/卡住时才调用 A* 重规划。

这不是 ROS Nav2 那种成熟的持续代价地图系统。

## 二、问题 1：抓取对准 + 机器人怎么找到要抓的物品

### 1.1 为什么右手指先碰到瓶子

代码确实允许较大的横向误差：

```python
kele 抓取配置：
grasp_max_lateral_close_err = 0.030   # 合爪时允许 3cm 横向误差
```

且我们的迭代记录明确写着：
- 最后采用 `creep_heading_lock = base_yaw`（冻结底盘航向）；
- 横向残差约 1.3cm；
- 靠闭爪容差吸收。

**翻译成人话**：最后阶段不是"物体始终在两指正中间"，而是：
1. 相机+运动学算出一个目标位置；
2. 底盘往前蠕动；
3. 航向早期锁定（避免近距离转向扫到瓶）；
4. 横向小误差不再充分修正；
5. 误差在 3cm 内就直接合爪。

对瓶子（半径 2.65cm）来说，1~3cm 偏差已经很大，一侧手指先碰到完全可能——**你说的"靠运气、拿指尖夹住"是对的**。

### 1.2 正确的改法：不要只调深度

历史上把前向偏移从 0.042 → 0.053 → 0.060 试过，结果从 4/5 掉到 1/5——**单纯改深度解决不了横向对中**。

正确方向：**增加"腕部视觉伺服"（末端闭环对中）**：
1. 头部 RGB-D 把机械臂送到目标前方 8~12cm；
2. **开启右腕相机**（现在没用！）；
3. 在腕部图像里检测目标中心；
4. 算目标中心与两指中线的像素误差；
5. 优先用**机械臂小范围横向修正**（不是整个底盘贴着货架转向）；
6. 连续多帧满足（横向误差 < 8~10mm、朝向误差小、深度进抓取窗口）才合爪；
7. 对不中就退回预抓取点重新识别，**不要硬夹**。

> ⚠️ 在闭环没做出来前，**不要**直接把 3cm 门限改成 8mm，否则机器人可能永远不合爪。

### 1.3 它是怎么找到要抓的商品的（完整逻辑）

**指令来源**：服务器发布任务清单（本局 5 个可乐）→ 决策器按顺序选 → 客户端执行。

**两种模式定位方式**：
| 模式 | 怎么知道商品在哪 |
|---|---|
| 可视化（GT） | 仿真直接告诉（runtime_layout + gt 后端）——**不是真识别** |
| 正式（YOLO） | 头部相机 YOLO 检测 + 深度 + FK + ArUco 绑定货架格——**真识别** |

**注意**：你平时看的可视化窗口用的是 GT，所以机器人"想拿哪个就拿哪个"、位置精确；正式比赛要靠相机自己找，难度高很多。

## 三、问题 2：撞倒物品后 360° 转身 + 爪子中间的摄像头

### 2.1 为什么转 360°

**不是"观察环境"**，代码里没有这种设计。最可能的是导航恢复的叠加：
1. 检测到几乎没位移 → 判定卡住；
2. 倒车 → 定时旋转 → 重规划；
3. 新方向仍被挡 → 再恢复；
4. 多次定时旋转叠加（每次 ~1~4 秒），视觉上接近甚至超过 360°。

恢复代码在：
- `run_recovery_motion()`
- `maybe_start_stuck_recovery()`

**推荐改法**：把"转多少秒"改成"转到目标角度"：
```
记录当前 yaw → 目标 yaw = 当前 ± π → 用里程计闭环转向 → 到角度误差阈值就停
```
再加"恢复动作冷却时间"，避免刚结束又立刻进入恢复、连续旋转。

### 2.2 爪子中间的摄像头有用吗

**目前没用**。服务器能渲染左右腕部相机（`SUPERMARKET_RENDER_ALL_CAMERAS=1`），但：
- 默认只渲染头部相机；
- 感知节点只订阅头部 RGB-D；
- 客户端没订阅腕部 RGB；
- 腕部没有深度流；
- 没有手眼标定和像素误差控制器。

所以它现在"看"爪子对准的方法是：**头部相机估计物体位置 + 关节角算末端位置 + 预设几何偏移**。爪子中间那个摄像头目前是"摆设"——这正是上面 1.2 说的要开发的方向。

## 四、问题 3：放置后后退太短、转身太急

这是当前代码里**非常明确的问题**：

```python
PLACE_REVERSE_DISTANCE = 0.07   # 只后退 7cm
```

7cm 只够指尖离开瓶身，**完全不足以保证**张开的手指、手腕、小臂、肘部、以及转身时整个手臂的扫掠区域不碰到瓶子。

另外放置坐标当前是 `0.0, 0.12, 0.24, 0.12, 0.24`——**第四件复用第二件位置，第五件复用第三件**。如果前面放的商品还在桌上，就有重叠碰撞风险。

### 推荐：增加独立的 `POST_PLACE_EGRESS`（放置后安全撤离）阶段

```
开爪
→ 等待商品稳定
→ 保持底盘朝向不变，直线后退 0.18~0.30 m
→ 同时缓慢抬高并收回机械臂
→ 检查末端和肘部都离开桌面危险区
→ 完全收臂
→ 降低角速度再开始转身
```

其他配套：
- 五件商品用**五个真正不同的放置位置**；
- 记录已放商品的位置，导航和转身时把它们也当障碍；
- 手臂没收好时，底盘角速度限制在 0.2~0.3 rad/s，降低角加速度，避免甩肘；
- **可视化模式和正式模式的放置后收臂行为要统一**（现在不完全相同，会造成可视化通过、正式模式却不同表现）。

## 五、问题 4：撞箱子卡死 + 记住路径 + 树形回退

### 5.1 为什么撞箱子后卡死

你的判断正确，当前恢复逻辑不完整：

1. **障碍记忆很短**：雷达 7 秒、深度 3 秒——绕过去之后，之前箱子点的记忆就消失了；
2. **默认不是全程 A\***：平时优先走预设走廊，撞到才切换规划 → "按走廊靠近箱子 → 被挡 → 倒车 → A* → 又卡"；
3. **没有真正的死胡同回退**：当前是"短倒车 → 转向 → 重规划"，失败 3 次后进入 escape（0.22 m/s 倒车 6 秒 + 定时转 4 秒）。**最危险的是 escape 会绕过后方阻挡检查**——为了强制脱困，可能在不能确认后方安全时持续长倒车。

### 5.2 能不能"记住"第一次走通的路

**可以，而且值得做**，但不要简单重放速度指令。正确做法：
- 构建**本局持续存在的代价地图**（不是几秒就忘的临时记忆）；
- 保存第一次实际无碰撞通过的路径点作为**优先路线**；
- 每次出发前用雷达检查路线是否被挡，被挡就局部重规划；
- 成功绕行后更新缓存路线。

这样既省时间又安全，且符合"动态避障"要求（机器人仍在实时检测、必要时重规划）。

### 5.3 树形回退（你说的"回退一个节点"）

思路完全合理，但**不需要真的建一棵复杂的树**，用"面包屑安全路径"即可：

1. 行驶时每隔 0.2~0.3m 记录一个安全位姿（面包屑）；
2. 记录每条边是否无碰撞通过；
3. 发生碰撞 → 标记当前边/区域不可通行；
4. 停止后沿最近一次实际走过的安全路径**反向回退**；
5. 回到最近的高净空节点；
6. 把失败区域加入持久代价地图；
7. 从安全节点重新跑 A*；
8. 新路径仍失败 → 继续回退到更早节点；
9. 超过次数 → 安全放弃当前任务，而不是无限转圈。

这就是你说的"当前节点所有方向都走不通就退回父节点"——比原地试不同方向可靠得多。

## 六、大赛官方问题：障碍位置会变吗？路径规划怎么做？

### 6.1 同一场仿真障碍位置会变吗

**本仓库的本地服务器**：同一场仿真中，箱子初始位置**不会自动每趟重新随机**（随机化只发生在服务器启动时）。但箱子可能被机器人碰撞推动，所以后续位置可能变化。

**正式比赛服务器是否完全一样，必须以大赛方官方说明和镜像为准**——仓库里的只是二次开发实现，不能只凭它断言。

### 6.2 现在的路径规划怎么做

- **平时**：走预设走廊（几条固定的安全通道）；
- **撞到/卡住**：调用 A* 从当前位置重规划；
- **局部避障**：雷达/深度检测到近处障碍会减速或停下；
- **不是持续建图**：障碍记忆只有几秒，没有成功路线长期缓存，没有面包屑回退。

所以它更像"预设路线 + 出问题再重新算"，不是"实时感知地图 + 动态规划"的完整导航系统。

## 七、学习与协作：哪些是官方的、哪些是自己写的、怎么同步

### 7.1 哪些是官方/基础环境提供的

很可能（以官方仓库为准）：
- DISCOVERSE/MuJoCo 仿真框架；
- MMK2 机器人模型；
- 正逆运动学基础（FK/IK）；
- ROS2 话题桥接；
- 货架、机器人和比赛场景资产；
- server/client Docker 镜像；
- `/supermarket_sorting/task` 等比赛接口；
- 评分服务器和正式任务生成逻辑。

### 7.2 哪些是这个仓库明显自行开发/大幅修改的

- `decision/task_manager.py`、`decision/order_scheduler.py`（任务调度）；
- `perception/kele_detect.py`、`perception/inventory.py`（感知）；
- 自定义 YOLO 训练和数据生成脚本；
- `navigation/grid_planner.py`（A* 导航）；
- 大型 `supermarket_sorting_client.py` 状态机（抓取/放置/恢复逻辑）；
- 本地 referee（裁判）；
- 可视化/smoke/官方风格测试脚本；
- 审计文档和回归测试。

> 精确区分"哪一行是官方、哪一行是你们写的"，需要官方原始源码再做目录级对比；仅凭当前 Git 历史无法逐行区分（第一次提交就是完整导入）。

### 7.3 团队怎么同步开发

**GitHub 只作为"你们自己的客户端源码和配置"的唯一真源**。

上传到 GitHub 的：
- 客户端源码；
- 启动脚本；
- 参数配置；
- Dockerfile 或官方 client 镜像版本说明；
- 依赖锁定文件；
- 模型训练脚本和数据格式说明；
- 测试代码；
- README；
- 每次实验的随机种子、提交号和结果。

**不要提交到 Git**：
- 日志；
- 运行时生成的 `runtime_layout`；
- 数据集；
- 视频；
- 大模型权重（`.pt`/`.pth`，.gitignore 已排除）；
- 大赛方禁止再分发的镜像或资产。

**注意**：`.gitignore` 排除了 `*.pt`/`*.pth`，所以仓库里**没有**正式模式需要的：
```
examples/supermarket_sorting/perception/checkpoints/
supermarket_multiclass.pt
```
同学只 `git clone` 拿不到正式感知权重——需要单独传（或官方提供）。

**推荐的 Git 协作流程**：
- `main` 只保留已验证版本；
- 每个问题独立分支（`feat/wrist-visual-servo`、`fix/post-place-egress`、`feat/nav-backtracking`）；
- 每次修改走 Pull Request 合并；
- 禁止几个人同时直接改 6300 行主客户端；
- 每个 PR 附：seed、测试商品、成功率、是否碰撞、每单耗时、日志路径、修改前后对比；
- 稳定版本打标签（如 `baseline-v70`）；
- 不要用强制推送覆盖同学的提交。

## 九、结论：现在能不能提交？

**可以作为阶段性源码存档或内部评审版本提交，但不建议作为正式比赛最终版提交。**

理由：
1. 当前可视化脚本用 GT、运行时布局和裁判 oracle；
2. 仓库记录的稳定基线仍是 4/5（不是 5/5）；
3. 匿名任务和九分类 YOLO 尚未完整验证；
4. 九分类权重没跟随仓库；
5. 第五单受 600 秒时限影响；
6. 放置点重复；
7. 仍存在碰倒、撞箱、转圈和卡死；
8. 正式行为与可视化行为存在分支差异；
9. 部分控制逻辑读 `/referee/state`，需确认正式服务器是否提供、规则是否允许；
10. 缺少多随机种子、多类别、不同障碍布局的正式回归结果。

**最终交付通常至少包含**：客户端代码或镜像、一键启动脚本、运行依赖、模型权重、参数、说明、不依赖自行修改的 server/referee、官方 server 镜像上的复现结果。**具体以大赛方最新通知为准。**
